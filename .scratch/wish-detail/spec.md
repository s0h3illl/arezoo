# Spec: A wish's own page

Status: ready-for-agent

## Problem Statement

A wish has no address of its own. It exists only as a card on its owner's profile — there is no URL to send someone that says "this one, specifically," no page a contributor can be pointed back to, and no way to see a wish's full contributor list without wading through the whole grid it lives on. `wish-detail.dc.html` arrived as a finished-looking design for this page, drawn against a different app: no Tailwind, no `AppLayout`, a `showAmounts` flag Visibility doesn't have, a `/w/:wishId` slug column that doesn't exist, and a contribute modal with no server behind it anywhere in this codebase. Charting this effort ([The destination and the shape of the page](issues/00-charting.md)) settled what survives contact with the domain: a read-only page plus the owner's existing edit and delete controls, reached by id, with the contribute flow cut out entirely as a separate effort's job.

Two smaller gaps surfaced once the shape was settled. First, nothing in the app writes relative time — every date on every page is absolute — so «۲ روز پیش» needs a source, and it has to avoid going stale in a way nothing here has had to solve before. Second, and the one this spec treats as load-bearing: a wish page is the first place a contributor's identity is rendered to a reader who is not staff, and Visibility ([ADR-0010](../../docs/adr/0010-visibility-hides-identity-never-amount.md)) exists specifically to keep some of those identities out of the wrong hands. Inertia ships props into the HTML document itself, so masking in the Vue template would not be masking at all — it would be publishing the data with a stylesheet over it, the same mistake the shared `auth.user` prop made before `.scratch/edit-a-wish/issues/01-narrow-the-shared-user.md` fixed it.

## Solution

`GET /wishes/{wish}`, named `wishes.show`. A wish card, its funding folded into the card rather than floating beside it (the CTA that justified a separate card is gone), and a contributor list that infinite-scrolls the same way the profile grid does. Owner-only edit and delete reuse the components the profile grid already ships. A contributor a reader may not see renders as «ناشناس» with a real, visible amount — Visibility governs identity, never money — and the masking happens once, server-side, in a resource that never puts a withheld name in the response for a client-side stylesheet to hide.

Reached from the profile grid: a card's cover and title become links to its wish page, and the card's share button — which today shares the profile it sits on, because a wish never had its own address to share — now shares the wish instead.

## User Stories

1. As anyone with a link, I want to open a wish on its own page, so that I can see what it is and how it's doing without going through its owner's whole profile.
2. As a guest, I want the same page a signed-in reader sees, so that an account is never the price of finding out what a wish needs.
3. As a reader, I want a masked contributor's identity to genuinely never reach my browser, so that "hidden" means hidden and not merely undrawn.
4. As a reader, I want to see a masked contribution's real amount, so that I can tell a wish got real support without needing to know from whom.
5. As the wish's owner, I want to see a name Visibility hides from everyone else, so that "owner only" means I am the one exception.
6. As a reader, I want the contributor list to load a first page and then more as I scroll, so that a wish with hundreds of contributors doesn't ship them all in the document at once.
7. As a reader, I want the count above the list and the rows below it to always agree, so that the two numbers never contradict each other on the same page.
8. As a reader, I want a link to the product itself when the owner gave one, so that I can see what I'd be contributing towards.
9. As anyone sharing a card from the profile grid, I want the share button to hand over the wish's own link, so that the person I send it to lands on the thing I meant to share, not on its owner's whole profile.
10. As a reader who follows a stale or blocked-owner link, I want the same 404 the rest of the app already shows for a missing resource, so that a dead wish link doesn't look different from any other one.

## Implementation Decisions

### Reading the route

- **`GET wishes/{wish}` → `WishController::show()`, named `wishes.show`.** No middleware, no `->can(...)` — the first public read on a controller whose other three actions are writes behind `auth`. Placed between `wishes.store` and `wishes.update` in `routes/web.php`.
- **The `{wish}` parameter gets a global binding**, in `AppServiceProvider::configureRouteBindings()`, mirroring the `user` and `username` bindings already there: `Wish::query()->whereHas('owner', fn (Builder $q) => $q->excludingBlocked())->findOrFail($value)`. A soft-deleted wish already 404s for free — `Wish` uses `SoftDeletes`, and implicit binding excludes a trashed row without any code here. Applying the scope globally rather than only on `show()` is harmless: `wishes.update` and `wishes.destroy` both require an authenticated owner already, and `SignOutBlockedUsers` signs a blocked user out, so neither route was ever reachable by the account this excludes.
- **A pre-existing leak this map found is already fixed.** [Who may read a wish page](issues/02-who-may-read-a-wish-page.md) found `ProfileController` binding a plain `User` with no scope, leaking a blocked owner's profile. That's no longer true: `Route::bind('username', ...)` in `AppServiceProvider` already applies `excludingBlocked()` — landed in a later commit than the ticket, verified by `tests/Feature/ProfileTest.php`'s `'a blocked user has no profile'`, which passes today. Nothing to build there; this spec's only route-binding work is the new `wish` binding above, following the same pattern.
- **A soft-deleted owner is a documented consequence, not a line of code.** `.scratch/contributions/issues/05` still owes `User` its `SoftDeletes`. Once it lands, `whereHas('owner', ...)` and the `username` binding's own `User::query()` both start excluding a trashed owner automatically — Eloquent's global soft-delete scope reaches into a `whereHas` subquery the same as any other query. No code in this spec anticipates it; it falls out for free the same day that ticket adds the trait.
- **The 404 page is the shared, generic one.** `Error.vue` already renders one message per status code for every resource in the app; a missing or blocked-owner wish gets «این صفحه پیدا نشد» like anything else, per [Who may read a wish page](issues/02-who-may-read-a-wish-page.md).

### The public contribution

- **`App\Http\Resources\ContributionResource`, unnamespaced** — public, per [The server shape for the wish page](issues/05-the-server-shape.md)'s convention that admin is the exemption by namespace, never by name. It takes the model alone and works out the reader from the request itself. **Amended after building:** the spec had it take a `readerIsOwner` bool from outside — see the `ContributionCollection` bullet below for why that was abandoned.
- **A row is a discriminated union on `state`, and the withheld keys are absent, not nulled:**

    ```
    { id, state: 'visible',   name, avatar, amount, settled_at, settled_label }
    { id, state: 'anonymous',               amount, settled_at, settled_label }
    ```

  `state` resolves to `visible` when the contribution is `Public`, or `OwnerOnly` and the reader is this wish's owner; otherwise `anonymous`. `name` and `avatar` exist as keys **only** on a `visible` row — a reader who may not see a name gets no key for one, so there's nothing in `data-page` a stylesheet could be hiding. `amount` and `settled_at` are unconditional on every row: Visibility governs identity alone, never money ([ADR-0010](../../docs/adr/0010-visibility-hides-identity-never-amount.md)). No `message` key anywhere — a message is narrower than identity ([The server shape for the wish page](issues/05-the-server-shape.md)), and nothing on this page draws one regardless.
- **`state: 'deleted'` is decided and not built.** [What a contributor row shows](issues/03-what-a-contributor-row-shows.md) settled that a departed contributor reads as «کاربر حذف‌شده», visibly distinct from «ناشناس» — but `Contribution::contributor()` has no `withTrashed()`, and `users` has no `deleted_at` column, so no soft-deleted contributor can exist yet and nothing can hit that branch. The resource does not attempt it: there is no `trashed()` method to call on `User` until `.scratch/contributions/issues/05` adds `SoftDeletes` there. Whoever lands that ticket adds the third branch here; this spec leaves a comment pointing at it rather than guarding against a method that doesn't exist yet.
- **The date is two fields, not one.** [How this app writes «۲ روز پیش»](issues/01-writing-relative-time.md) found that Carbon's `diffForHumans()` — locale `fa`, already live at boot with nothing of this app's own configuring it — picks the unit and the wording, but returns Latin digits, fixed by one `NumberFormatter('fa', NumberFormatter::DECIMAL)` pass. Per that research, "the relative string is a second field, not a replacement": `settled_at` ships the raw ISO timestamp for a `<time datetime>` element, and `settled_label` ships the formatted Persian string (`«۲ روز پیش»`) beside it. Both live as private methods on `ContributionResource` — the only caller, so no new `app/` subfolder is introduced for a two-line helper.
- ~~**`App\Http\Resources\ContributionCollection extends ResourceCollection`**~~ — **abandoned, not built.** The class existed only to carry a `readerIsOwner` bool from the controller to every row, guarding against "two rows disagreeing". They cannot: every row in a response reads the same request and the same wish, so there is exactly one answer to derive. The row derives it itself — `$request->user()?->id === $this->wish->user_id`, private to `ContributionResource` — which keeps the whole visibility rule in the one class that enforces it and means no caller can serialise a contribution and forget to say who is looking. The cost is one eager-load: `->with(['contributor', 'wish'])`, one query per page, not one per row.
- **Ordering is `settled_at` descending**, per [What a contributor row shows](issues/03-what-a-contributor-row-shows.md): `created_at` marks when a gateway attempt began, not when it verified (ADR-0005), and a paid-only list's natural order is by when the money landed.

### The controller's props

- **Three props**, per [The server shape for the wish page](issues/05-the-server-shape.md): `wish` (`WishResource`, unchanged — `$wish->loadSum('paidContributions as received_total', 'amount')` satisfies its `LogicException` guard, since route-model binding hands the controller a bare model rather than a query it could chain `withReceivedTotal()` onto), `owner` (`UserResource`, a **sibling** prop via `$wish->load('owner')`, not nested inside `WishResource`), `contributions` (`Inertia::scroll()` over `$wish->paidContributions()->with(['contributor', 'wish'])->orderByDesc('settled_at')->paginate(7)`, handed straight to `ContributionResource::collection()`). The controller says nothing about who is reading — that is the resource's own question, per the bullet above.
- **7 rows per page**, matching [How many contributors the page loads](issues/04-how-many-contributors-load.md) — denser than the profile grid's 12-per-page cards, deliberately.
- **The count pill reads `contributions.meta.total`, not a model method.** A person who gives twice is two rows and counts twice in the pill too, so the pill and the list can never disagree — the label is «مشارکت» (contribution), not «نفر» (person), because it now counts rows rather than people. The `Wish::contributorCount()` this once named no longer exists: on 2026-09-09 the whole app stopped counting people, and the model method became `Wish::contributionCount()` — see ADR-0014, which generalises the decision this page made first.

### The page

- **`WishDetail.vue`**, `Inertia::render('WishDetail', ...)` — named for the working name this effort has used throughout (`.scratch/wish-detail/`, the throwaway prototype's own route and folder).
- **Layout: Variant B**, the prototype's winning variant from [The layout in the real stack](issues/07-the-layout-in-the-real-stack.md). The funding card does not survive losing its contribute CTA — a summary row, a bar and a meta line aren't enough to justify a bordered card of their own — so the money dissolves into the wish card as a `rounded-2xl bg-slate-50` block between the title row and the description. The two-column grid (`repeat(auto-fit, minmax(320px, 1fr))`) is otherwise unchanged; the right column holds the contributor card alone.
- **Money block:** received amount and «از {price}» on one line, percentage at the row end (same weight, so the two figures read as a pair); `h-2.5` track, emerald fill; one meta line below — «{remaining} تومان مونده» or «تکمیل شد». **The bar clamps at 100%; the percentage figure does not** — `formatShare`/`formatToman`/`shareOf` from `resources/js/lib/format.ts` are reused unchanged, and over-funding shows «۱۴۰٪» the same way the profile grid already does, per [The destination and the shape of the page](issues/00-charting.md).
- **Photo**, `clamp(220px,32vw,320px)` tall, full-bleed, falling back to the shipped `wish-cover-placeholder` stripe; the «برآورده شد!» badge at ≥100%.
- **Buy link.** The design draws a row for `wish.link` under the description that no ticket in this map separately grilled — but the field already exists (`purchase_link`), `WishResource` already publishes it, and `resources/js/types/wish.ts`'s own comment already anticipates it: *"shown on the wish detail page rather than on a card."* `.scratch/edit-a-wish/spec.md` named this page by name as where the field belongs, in its own Out of Scope. Rendered when set, as a plain external link (`target="_blank" rel="noopener"`), omitted when not — a direct, low-risk translation of an existing field into an already-drawn row, not a new design question.
- **Contributor card:** head with the «{n} مشارکت» pill; `<InfiniteScroll data="contributions" items-element="#contributor-list">`; a `ContributorRow.vue` per row — `visible` gets the app's own real-picture-or-emerald-initial avatar (`Profile.vue`'s existing pattern, not the design's cycling palette), name, relative date (`<time :datetime="row.settled_at">{{ row.settled_label }}</time>`), and amount; `anonymous` gets a slate avatar with «؟», the name «ناشناس», and the **same real amount** beside it. Empty state: «هنوز کسی کمک نکرده», no CTA, pill at «۰ مشارکت» — per [How many contributors the page loads](issues/04-how-many-contributors-load.md), since no contribute action exists on this page for the design's «اولین نفر باش» to invite.
- **No owner controls on this page.** The design draws edit and delete buttons beside the title, and an earlier draft of this spec specified them; that was reversed. The wish's own page is a read-only view for everyone, its owner included — editing and deleting stay on the profile grid, which is the one place a wish is managed from. `EditWishDialog` and `DeleteWishDialog` keep their profile-only trigger styling and are not imported here.
- **«برگشت به پروفایل» via `setHeaderNav()`** — the existing mechanism `Home.vue` already uses for its own header links, not a new `AppLayout` slot. Found while prototyping ([The layout in the real stack](issues/07-the-layout-in-the-real-stack.md)).
- **`WishController::update()` keeps its `to_route('profile', $request->user()->username)`.** A draft of this spec changed it to `redirect()->back()` so an owner editing from the wish page wouldn't be bounced away; with the owner controls dropped, the profile grid is once again the only surface an edit is submitted from, and the hard-coded redirect is correct as it stands. `destroy()` is likewise untouched.

### Reaching the page

- **A card's cover and title become `<Link :href="show(wish.id)">`** (`@/routes/wishes`), per [The destination and the shape of the page](issues/00-charting.md). The footer's edit, share and delete controls stay buttons outside that anchor — nesting three buttons and two dialogs inside a link was rejected there.
- **The card's share button now shares the wish, not the profile it sits on.** Per [Sharing a wish](issues/06-sharing-a-wish.md): `shareProfile()` is **deleted**, not rehomed — it had exactly one call site, and pointing that site at the wish's own link doesn't relocate profile-sharing, it ends it. The private `share(path)` in `useShare.ts` is promoted to the module's export as **`shareLink(path: string)`**; `WishCard.vue` calls `shareLink(show(wish.id).url)` with `aria-label="اشتراک لینک آرزو"`. The toast copy is untouched — it was already link-generic. The stray trailing `#` `shareProfile()` used to resolve goes away by construction, since the surviving caller passes a real path.
- **The wish page gets no share control of its own.** The design draws none, and the page is arrived at by URL, which is already in front of whoever is reading it. Recorded consequence, per [Sharing a wish](issues/06-sharing-a-wish.md): `navigator.share`'s native sheet is reachable from a card and not from the wish's own page.

## Testing Decisions

- **The load-bearing test: a masked contributor's identity never reaches the response.** Feature test asserting an `anonymous` row's JSON has no `name` or `avatar` **key** — not a null value — while its `amount` and `settled_at` are present. This is the assertion that stops the leak coming back, the same role `.scratch/edit-a-wish/spec.md`'s shared-user test plays for `auth.user`. Read the response, not the DOM — a masking bug that only fails a browser assertion would still have shipped the name into the HTML document.
- Feature test: an `owner`-visibility contribution is `visible` to the wish's owner and `anonymous` to a guest and a signed-in visitor, from the *same* response for the *same* wish — the guest case covering the null-reader path the resource has to answer for itself.
- Feature test: guest, signed-in visitor and owner all read `wishes.show` for an existing wish; a soft-deleted wish 404s; a wish owned by a blocked user 404s.
- Feature test: rows arrive ordered by `settled_at` descending.
- Feature test: `contributions.meta.total` counts every paid contribution regardless of visibility, and matches what the pill reads.
- No new `EditWishTest` coverage: `update()` keeps its hard-coded profile redirect, so the existing assertions hold unchanged.
- Browser test: a visitor clicks a card's cover or title on the profile grid and lands on that wish's own page.
- Browser test: nobody — owner, signed-in visitor or guest — sees edit or delete controls on the wish's own page. The owner case is the one that guards the reversal, since that is the reading the design and the earlier draft both got wrong.
- **Not tested: the share button's new target.** Confirming `shareLink` receives the wish's URL rather than the profile's would need a `navigator.share`/clipboard stub the Pest browser plugin has no precedent for anywhere in this app — `data-test="share"` has no assertion behind it today either, per [Sharing a wish](issues/06-sharing-a-wish.md). Flagged rather than worked around.
- No file upload is exercised by any browser test this spec adds — the Pest browser plugin still can't drive a multipart submission (`.scratch/edit-a-wish/spec.md`'s own testing decision), and nothing here changes that.
- `php artisan migrate:fresh --seed` completes, Pint clean, larastan clean, `bun run types:check` clean.

## Out of Scope

- **Taking money.** The contribute modal, the payment gateway, the callback, verification and the failure path belong to a separate `.scratch/contribute/` effort, which does not exist yet. Nothing in the app creates a `Contribution` today, and this spec does not change that.
- **Lists.** The design's breadcrumb, its «از لیست X» chip, private lists and share tokens are all cut; no breadcrumb is rendered at all. `CONTEXT.md` is unambiguous that a profile holds every wish a user publishes, with no grouping between the two.
- **Re-specifying the edit modal.** `EditWishDialog.vue` already ships §5's fields. Its price-change warning and progress-delta callout are a change to a shared component, wanted on the profile grid as much as here, and belong to their own small effort.
- **A typed-confirmation delete with a refund warning.** ADR-0003 means deleting refunds nothing and destroys no contribution; `DeleteWishDialog` already says the true thing.
- **A deleted contributor's «کاربر حذف‌شده» treatment.** Decided (above), not buildable: blocked on `.scratch/contributions/issues/05` giving `User` its `SoftDeletes` and `Contribution::contributor()` its `withTrashed()`.
- **A soft-deleted owner's 404.** Also blocked on the same ticket, and also requires no code of its own once it lands — see "Reading the route" above.
- **Meta tags for a sent link.** Nothing in the app sets an OG title, description or image on any page today; this is a platform-wide gap, not one specific to this page, and belongs to its own pass rather than this spec.
- **Refreshing a stale relative-time label.** [How this app writes «۲ روز پیش»](issues/01-writing-relative-time.md) found that a server-written string goes stale on a page left open, and that nothing in this app polls or re-renders on a timer. This page doesn't start that pattern — a stale «۲ دقیقه پیش» is accepted the same way an absolute date on every other page in the app never needed refreshing, because nothing here has needed it either.
- **The `contribute` effort's CTA.** See Further Notes for the contract this spec hands it.
- ~~**Fixing the admin panel's `Contribution` type living outside `@/types/admin/`.**~~ Flagged below in Further Notes as a pre-existing inconsistency this spec works around, not one it corrects. **Amended after building: it was corrected**, in a follow-up pass — see that note.

## Further Notes

- **The handoff to `.scratch/contribute/`.** This spec records the funding card's shape without a CTA in it, per [The destination and the shape of the page](issues/00-charting.md): a summary row, a bar, and a meta line, now living inside the wish card rather than beside it (Variant B). Whoever builds the contribute flow adds a button into that same block once it exists — where exactly, and what it posts, is that effort's decision to make once it has a server behind it, not this one's to anticipate further.
- ~~**A frontend type-naming collision, worked around rather than fixed.**~~ **Amended after building: fixed rather than worked around.** The spec argued that because the admin panel's `Contribution` type sat at `resources/js/types/contribution.ts` — the top level, not `@/types/admin/`, unlike `Admin\UserResource`'s and `Admin\WishResource`'s mirrors — the public type needed a name of its own (`Contributor`, as built, after the spec's `ContributorRow`). A follow-up pass moved the admin shape to `resources/js/types/admin/contribution.ts` instead, where its siblings already were, freeing `resources/js/types/contribution.ts` for the public row and deleting the one-off type entirely. The page moved with it, to `resources/js/pages/wishes/Show.vue`.
- **The row is nested, and carries no contributor id.** Following from the above, `contributor` is a `Pick<User, 'name' | 'avatar'>` rather than `name` and `avatar` flat on the row, and the contributor's **`id` is published nowhere**: no page links to a contributor's profile, so leaving it out means a masked row cannot be traced back to a user through the payload — the same reasoning as the masking itself, one step further. The keys-absent-vs-values-masked question the spec settled earlier is unchanged: an anonymous row carries «ناشناس» and a null avatar, not withheld keys, so `state` remains the single discriminator.
- `.scratch/contributions/issues/05` is a dependency this effort does not own, named twice above: it owes `User` a `SoftDeletes` trait and `Contribution::contributor()` a `withTrashed()`. Both the deleted-contributor row and the soft-deleted-owner 404 are decided in this spec and wait on it.
